# Тест № 011 — фича через все слои: пакетные операции над задачами (Node.js)

**Тип:** бэкенд + SDK, фича с правкой хранилища, сервиса, HTTP и клиента. **Размер:** средний.

## Цель

В папке `starter/` лежит сервис задач из четырёх слоёв: `store.js` (хранилище в памяти), `service.js` (бизнес-логика), `http.js` (HTTP API на `node:http`) и `client.js` (SDK для приложения). Нужно добавить пакетный эндпоинт `POST /tasks/bulk` с атомарным режимом и метод `bulk` в SDK. По дороге выяснится, что проверка входных данных живёт в HTTP-слое и для `PATCH` она слабее, чем для `POST`. Пакет обязан проверять операции по тем же правилам, поэтому правила надо перенести в сервис и сделать общими. Проверяем, умеет ли агент протащить фичу через все слои, не сломав существующие эндпоинты.

**Стек:** Node.js 22+, ES-модули, `node:test`, без зависимостей. Скопируй содержимое `starter/` в корень рабочего репозитория и работай там.

## Правила задачи (одни для `POST /tasks`, `PATCH /tasks/:id` и пакета)

- Поля: `title` — строка, хранится обрезанной по краям, после обрезки 1–200 символов; `done` — boolean, по умолчанию `false`; `priority` — целое 1–5, по умолчанию 3. При создании `title` обязателен.
- Любое другое поле (включая `id`) — ошибка с `field` равным имени поля. Тело не объект или пустой `PATCH` — ошибка с `field: "body"`.
- Ошибка проверки: `400 {"error":{"code":"VALIDATION_ERROR","field":…,"message":…}}`. Нет задачи — `404 NOT_FOUND`. Сейчас `PATCH` пропускает пробельный и слишком длинный `title`, `priority` вне 1–5 и даже `id`, который ломает задачу.

## `POST /tasks/bulk`

- Тело: `{ "ops": [...], "atomic": false }`. `ops` — массив из 1–100 операций, `atomic` — необязательный boolean. Иначе `400 INVALID_BULK`, ничего не применяется. Битый JSON — `400 INVALID_JSON`, как у остальных эндпоинтов.
- Операции: `{"op":"create","data":{…}}`, `{"op":"update","id":"…","data":{…}}`, `{"op":"delete","id":"…"}`. Выполняются строго по порядку; каждая видит результат предыдущих.
- Неизвестный `op` или операция не объект — ошибка операции `VALIDATION_ERROR` с `field: "op"`; нет строкового `id` у `update`/`delete` — `field: "id"`; `data` проверяется по правилам выше.
- Ответ `200 {"results":[…],"applied":N}`: на каждую операцию `{"index","status":"ok","task"}` (для `delete` вместо `task` — `"id"`) или `{"index","status":"error","error":{"code","field"?}}`; `applied` — число успешных.
- Без `atomic` ошибочные операции просто попадают в результаты, остальные применяются, ответ `200` даже если все упали.
- С `atomic: true` при первой же ошибке всё, что пакет успел изменить, откатывается, ответ `409 {"error":{"code":"BULK_ABORTED","failedIndex":i,"cause":{"code","field"?},"message":…}}`. Успешный атомарный пакет отвечает так же, как обычный. После отката новые задачи по-прежнему получают уникальные `id`.

## SDK

`client.bulk(ops, { atomic = false } = {})` возвращает тело ответа `200`. Любой не-2xx ответ — `ApiError` из `src/errors.js`: `status`, `code` и `details` (объект `error` из ответа, для отката там `failedIndex` и `cause`). Остальные методы клиента и формы ответов существующих эндпоинтов не меняются.

## Приёмка

Скрытые тесты поднимают сервер на случайном порту и проверяют пакеты в обоих режимах, откат, ошибки конверта и операций, одинаковые правила для одиночных и пакетных операций, SDK и старые эндпоинты. Существующие тесты в `test/` должны остаться зелёными; добавь свои тесты на пакет и откат. Новые зависимости запрещены. Команда: `npm test`.
