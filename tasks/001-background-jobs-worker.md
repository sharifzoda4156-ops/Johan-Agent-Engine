# Тест № 001 — API фоновых заданий + worker

## Цель и границы

Создать изолированный учебный сервис обработки строк, чтобы проверить работу Johan с API, SQLite, конкурентностью, сбоями и тестами. Это отдельный проект, **не часть production Johan**.

**Стек:** Node.js 22+, Fastify, `better-sqlite3`, npm, `node:test`. API и worker — два отдельных процесса на одном хосте, общая SQLite-база (`DATABASE_PATH`; по умолчанию `./data/jobs.sqlite`). API слушает `PORT` (по умолчанию 3000).

Без внешних API, Docker/Kubernetes, UI, авторизации, Redis/RabbitMQ, платных сервисов и дополнительных функций. Обработка — подсчёт последовательностей непробельных символов в `text` по правилам JavaScript `\s` (для пустой строки/пробелов — 0). Внешних побочных эффектов нет.

## HTTP API

Общий формат ошибки: `{"error":{"code":"CODE","message":"Описание"}}`. Ответ с заданием: `{"id":"UUID","state":"queued","result":null,"attempts":0,"error":null}` (актуальные значения полей зависят от состояния). После успеха `result={"wordCount":N}`; в БД можно хранить числовой `result`.

| Метод | Условие | Ответ |
| --- | --- | --- |
| `POST /jobs` | `{"text":"Hello world"}` — новое задание | `201`, объект задания и `Location: /jobs/:id` |
| `POST /jobs` | тот же `Idempotency-Key` и точно тот же `text` | `200`, ранее созданное задание с тем же ID |
| `POST /jobs` | тот же ключ, но другой `text` | `409 IDEMPOTENCY_CONFLICT` |
| `GET /jobs/:id` | ID существует | `200`, объект задания |
| `POST /jobs/:id/cancel` | `queued` | `200`, состояние `cancelled` |
| `POST /jobs/:id/cancel` | уже `cancelled` | `200`, тот же объект задания |
| `POST /jobs/:id/cancel` | `running` | `409 JOB_ALREADY_STARTED` |
| `POST /jobs/:id/cancel` | `completed` или `failed` | `409 JOB_TERMINAL` |
| `GET /jobs/:id`, `POST /jobs/:id/cancel` | неизвестный UUID | `404 NOT_FOUND` |

Валидация: на создание принимается только JSON-объект ровно с одним полем `text` типа string, длина 0–10 000 UTF-16 code units; некорректное тело — `400 VALIDATION_ERROR`, неподдерживаемый Content-Type — `415`, превышение лимита HTTP-тела — `413`. Пустой текст допустим. `Idempotency-Key` необязателен; если указан — 1–128 символов, `[A-Za-z0-9._-]`, регистрозависимый; некорректный ключ — `400 VALIDATION_ERROR`. Невалидный формат UUID в URL — `400 VALIDATION_ERROR`.

## Состояния и worker

- `queued → running | cancelled`;
- `running → completed` при успехе;
- `running → queued` при ошибке обработки, если попытки ещё остались;
- `running → failed` при последней ошибке или истечении lease третьей попытки;
- `running` с истёкшим lease и доступными попытками → новый `running` с новым владельцем;
- `completed`, `failed`, `cancelled` — терминальные.

**Lease — 10 секунд, максимум 3 захвата/попытки.** `attempts` увеличивается только при успешном захвате. Worker атомарно выбирает `queued` либо `running` с истёкшим lease, устанавливает уникальный `claim_token`, `lease_until` и увеличивает `attempts`. Не держать транзакцию открытой во время обработки.

Завершение/ошибка записываются только при совпадении `claim_token`, состоянии `running` и неистёкшем lease. Запоздалый worker не может перезаписать чужой результат. Истёкший lease третьей попытки должен переводить задание в `failed` с причиной `LEASE_EXPIRED` без четвёртого захвата. При исчерпании повторов причина последней ошибки сохраняется. Обычный сбой процесса оставляет lease до истечения; после перезапуска работу подхватывает worker.

**Гарантия — корректный сохранённый итог, не exactly-once исполнение.** После падения возможен повтор обработки.

Использовать SQLite-транзакции и условные UPDATE для сериализации создания по ключу, отмены и захвата. В гонке отмены с захватом побеждает ровно один: либо `cancelled`, либо `running` и ответ `409` на отмену. Уникальность ключа обеспечивается ограничением БД, а не проверкой до вставки.

## Минимальная схема SQLite

```sql
CREATE TABLE jobs (
  id TEXT PRIMARY KEY,
  text TEXT NOT NULL,
  idempotency_key TEXT UNIQUE,
  state TEXT NOT NULL CHECK (state IN ('queued','running','completed','failed','cancelled')),
  attempts INTEGER NOT NULL DEFAULT 0 CHECK (attempts BETWEEN 0 AND 3),
  result INTEGER CHECK (result IS NULL OR result >= 0),
  error TEXT,
  claim_token TEXT,
  lease_until INTEGER,
  created_at INTEGER NOT NULL,
  updated_at INTEGER NOT NULL
);
```

Время — Unix milliseconds; нужны индексы для очереди и истёкших lease, `PRAGMA journal_mode=WAL` и `busy_timeout`. Допустимо добавить необходимые CHECK-ограничения; не расширять модель лишними таблицами.

## Приёмочные проверки (обязательные offline-тесты)

1. `POST /jobs` → реальный захват worker → `completed` → верный `wordCount` и `attempts=1`.
2. Повтор идентичного ключа/текста возвращает тот же ID; другой текст — 409; одновременные создания не дублируют задание.
3. Отмена `queued` исключает выполнение; управляемая гонка cancel/claim даёт ровно один допустимый исход.
4. Сбой worker после захвата и до сохранения → продвижение часов за lease → повторный захват → верный результат; устаревший `claim_token` отклоняется.
5. Постоянная ошибка → ровно 3 попытки, `failed`, сохранённая причина; отдельно — истечение lease на третьей попытке без четвёртого захвата.
6. Закрытие и повторное открытие реальной файловой SQLite-базы после перезапуска API/worker сохраняет задания, результаты, ошибки и ключи.

Тесты интеграционные, с временной файловой БД, настоящими SQL-операциями, управляемым временем и внедряемыми сбоями; не подменять всё моками. Без долгих `sleep` и сетевых зависимостей. Проверить корректное закрытие API и worker по SIGINT/SIGTERM. README реализации должен содержать `npm install`, запуск API и worker, тесты и примеры `curl`, включая восстановление после рестарта.
