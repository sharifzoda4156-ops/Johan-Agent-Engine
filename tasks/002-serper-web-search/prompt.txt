Задача: добавить веб-поиск в плейн-чат через Serper API. Тумблер, usage-учёт, rate limit.
Контекст: сейчас плейн-чат отвечает только из модели. Нужно дать агенту возможность искать в вебе через Serper (google-обёртка), с тумблером включения, учётом расхода и лимитом частоты. Это слой 3 из роадмапа.
Реализовать:
Новый модуль lib/webSearch.js.
Функция searchWeb(query, { num = 5 }) → зовёт Serper API (https://google.serper.dev/search, POST, заголовок X-API-KEY из env SERPER_API_KEY, тело { q: query, num }).
Возвращает нормализованный массив: [{ title, link, snippet, position }] из поля organic ответа Serper.
Обработка ошибок: нет ключа → понятная ошибка; таймаут (5с) → пустой результат + лог;非-200 → лог и пустой результат. Не роняй чат из-за поиска.
Оставь в коде чёткую точку расширения — комментарий // POST-PROCESSING HOOK там, где результаты Serper готовы, но ещё не отданы дальше. Сюда позже встанут фильтры/реранк/дедуп/кэш. Не реализуй их сейчас, только оставь место.
Тумблер в диспетчере.
В плейн-ветке /api/agent/ask (там, где чат идёт без репо-задачи) добавь возможность поиска. Включение — через флаг (env WEB_SEARCH_ENABLED глобально + возможность на юзера/чат, если в схеме уже есть похожий паттерн тумблеров — переиспользуй его, не плоди новый механизм).
Когда поиск включён: перед ответом модели дёрни searchWeb на основе запроса юзера, подмешай результаты (title + snippet + link) в контекст модели как справочный блок. Модель отвечает с учётом найденного.
Когда выключен — поведение как сейчас.
Usage + rate limit.
Каждый вызов Serper учитывай в usage (переиспользуй существующий механизм usageLimits / usage-таблицу, тем же паттерном, что для вызовов модели). Поиск — отдельная статья расхода.
Rate limit на вызовы поиска per user (например N/мин — возьми разумный дефолт, вынеси в env). Проверка ДО вызова Serper.
