# Тест № 010 — миграция схемы БД с переносом данных (Python + SQLite)

**Тип:** бэкенд, миграция схемы живой базы и правка слоя доступа к данным. **Размер:** средний.

## Цель

В папке `starter/` лежит хранилище заметок `notes_app` на SQLite: схема версии 1, слой `repo` и CLI. За время жизни в базе накопился мусор: email в разном регистре и с пробелами, дубликаты пользователей, теги строкой через запятую, заметки удалённых пользователей. Нужно ввести версионированные миграции, перевести базу на схему версии 2 с переносом данных и переписать `repo` под новую схему. Проверяем, умеет ли агент безопасно мигрировать данные: атомарно, идемпотентно и без потерь.

**Стек:** Python 3.11+, только стандартная библиотека (`sqlite3`, `unittest`). Скопируй содержимое `starter/` в корень рабочего репозитория и работай там.

## Схема версии 2

- `users(id, email, name, created_at)`: `email` хранится нормализованным (`strip().lower()`) и уникален.
- `notes(id, user_id, body)`: `user_id` ссылается на `users(id)` с `ON DELETE CASCADE`; колонки `tags` больше нет.
- `tags(id, name)`: `name` уникален, нормализован (`strip().lower()`, не пустой).
- `note_tags(note_id, tag_id)`: первичный ключ из пары, ссылки на `notes` и `tags` с `ON DELETE CASCADE`.
- Версия схемы хранится в `PRAGMA user_version`: 0 — пустая база, 1 — текущая схема, 2 — новая.

## Миграция

- `notes_app.db.migrate(conn) -> (было, стало)`: пустую базу (версия 0) создаёт сразу в версии 2, базу версии 1 переводит в 2, на версии 2 ничего не меняет и возвращает `(2, 2)`. Другая версия или непустая база с версией 0 — `MigrationError` (класс в `notes_app.db`). `init_db(conn)` делает то же, что `migrate`.
- Пользователи с одинаковым нормализованным email сливаются в пользователя с наименьшим `id`: его `name` и `created_at` сохраняются, заметки остальных переходят к нему, остальные удаляются. `id` выживших пользователей и всех заметок не меняются.
- Теги заметки из строки: разделить по запятой, нормализовать, выбросить пустые и повторы, сохранить порядок.
- Если есть заметка без существующего пользователя или email пустой после нормализации — `MigrationError`, и база остаётся ровно такой, какой была (схема, данные, версия). Любая другая ошибка в процессе — то же самое: миграция целиком в одной транзакции.
- База на 2000 пользователей и 30 000 заметок мигрирует за несколько секунд.
- `connect(path)` включает проверку внешних ключей.

## Слой repo после миграции

- `add_user(conn, email, name)` сохраняет нормализованный email; дубликат — `repo.DuplicateEmail` (наследник `ValueError`).
- `find_user`, `add_note`, `list_notes`, `delete_user` принимают email в любом регистре и с пробелами.
- `add_note(conn, email, body, tags=())` нормализует теги как миграция; неизвестный пользователь — `LookupError`.
- `list_notes(conn, email, tag=None)` → `[{"id", "body", "tags"}]` по возрастанию `id`, теги в порядке добавления. Фильтр по тегу — точное совпадение после нормализации (сейчас `py` находит и `python`). Неизвестный пользователь — `[]`.
- `delete_user` удаляет пользователя вместе с заметками и их связями с тегами.

## CLI

`python -m notes_app migrate DB`: печатает `migrated 1 -> 2` или `up to date (2)` и выходит с кодом 0; при `MigrationError` пишет в stderr строку, начинающуюся с `migration failed:`, и выходит с кодом 1. Команда `init` остаётся.

## Приёмка

Скрытые тесты собирают базу версии 1 с «грязными» данными, мигрируют и проверяют схему, данные, ограничения, откат при ошибке, повторный запуск, `repo` и CLI. Существующие тесты в `tests/` должны остаться зелёными; добавь свои тесты на миграцию. Новые зависимости запрещены. Команда: `python -m unittest`.
