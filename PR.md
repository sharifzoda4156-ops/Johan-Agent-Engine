# PR: fix/ttlcache-expiry-lru — багфикс TTL-кэша

## Изменено
- `ttlcache/cache.py`:
  - `_expired`: граница истечения `>=` вместо `>`.
  - `purge`: условие просрочки `exp <= now` (согласовано с `_expired`).
  - `get`: `move_to_end(key)` при попадании — обновление LRU-порядка.
  - `set`: ветка существующего ключа обновляет значение/`expires_at` и делает `move_to_end` без вытеснения; для нового ключа — `purge`, затем `popitem(last=False)` при `len >= maxsize`, затем вставка.
  - `set`: валидация `ttl <= 0` → `ValueError` до любых мутаций.
  - `__contains__`: учитывает срок жизни, удаляет просроченную запись, возвращает `False`.
  - `__len__`: вызывает `purge()` перед подсчётом.
  - docstring модуля: отметка о ветке `fix/ttlcache-expiry-lru`.
- `tests/test_cache.py`: 5 регрессионных тестов.

## Причины по каждому из 5 репортов (по одной строке)
1. Граница истечения TTL: `_expired` использовал `>` вместо `>=`, из-за чего запись жила ровно на один тик дольше — исправлено на `>=` и согласован `purge`.
2. LRU-порядок при `get`: попадание не вызывало `move_to_end`, поэтому часто читаемый ключ вытеснялся как самый старый — добавлен `move_to_end`.
3. Вытеснение при обновлении существующего ключа: `set` проверял `len >= maxsize` до вставки и вытеснял чужую запись — добавлена ветка обновления существующего ключа без вытеснения.
4. `__contains__`/`__len__` и просроченные записи: методы не учитывали TTL и не трогали счётчики — `__contains__` проверяет срок, `__len__` вызывает `purge`, `hits`/`misses` не изменяются.
5. Валидация `ttl` в `set`: `ttl <= 0` принимался молча — добавлен `ValueError('ttl must be > 0')` до мутаций кэша.
